# Frontend Modernization Learning

Use this instruction file to preserve durable lessons learned from reverse-engineering and frontend modernization work.

## Purpose

- Reverse engineering and modernization are iterative learning loops. When a failure mode is discovered, capture the corrective pattern here and reuse it by default on the next app.

## Path Selection Rules

- Discovered-source routing rule: when the current-state or solution-design evidence classifies the browser source as `server-rendered-app`, MVC, or Razor, route Step 12 through Path A first unless the approved MVC decomposition artifacts already exist and are still usable for the current lane.
- Discovered-source routing rule: when the current-state or solution-design evidence classifies the browser source as Angular, AngularJS, legacy Fusion G1, or another `browser-led-spa`, route Step 12 through the Angular browser-client decomposition path first unless the approved Angular decomposition artifacts already exist and are still usable for the current lane.
- Source-type routing rule: for MVC or Razor browser apps, require Path A decomposition first unless an approved decomposition contract already exists. Do not improvise Step 12 boundaries directly from raw views.
- Source-type routing rule: for Angular, AngularJS, legacy Fusion G1, or other browser-led SPA sources, require the Angular browser-client decomposition contract first unless an approved decomposition contract already exists. Do not improvise Step 12 boundaries directly from raw routes, modules, or component folders.
- Approved-contract rule: treat `.modernization/ignition-artifacts/MVC-To-Browser-Client-Decomposition-Contract.generated.json` as the authoritative Path A gate artifact and `.modernization/ignition-artifacts/MVC-To-Browser-Client-Decomposition-Contract.md` as its readable companion. For MVC or Razor apps, Path B is allowed only when the JSON contract exists, is current enough to trust, and is not known to be incomplete.
- Approved-contract rule: treat `.modernization/ignition-artifacts/Angular-To-Browser-Client-Decomposition-Contract.generated.json` as the authoritative Angular Path A gate artifact and `.modernization/ignition-artifacts/Angular-To-Browser-Client-Decomposition-Contract.md` as its readable companion. For Angular, AngularJS, legacy Fusion G1, or other browser-led SPA apps, Step 12 shell formation is allowed only when the JSON contract exists, is current enough to trust, and is not known to be incomplete.
- Path selection rule: once `.modernization/ignition-artifacts/MVC-To-Browser-Client-Decomposition-Contract.generated.json` exists and is usable, treat later Step 12 clicks as Path B remediation or validation loops, not a return to Path A.
- Path selection rule: once `.modernization/ignition-artifacts/Angular-To-Browser-Client-Decomposition-Contract.generated.json` exists and is usable, treat later Step 12 clicks as shell-formation remediation or validation loops, not a return to the Angular decomposition path.
- Step 10 loop rule: if screenshot, visual, weighted inventory, or weighted selector gates fail, keep the next step on Step 10 `Frontend Foundation & Scaffold`. Do not recommend Step 11 `Frontend Migration` unless all Step 10 gates pass or the user explicitly overrides.

## Remediation Rules

- ROI-first remediation rule: during Step 12 remediation loops, prioritize the biggest wins first. Focus on the lowest-rated screens and the highest-priority missing seams before low-value polish.
- Non-remediating-pass rule: if a Step 12 click only refreshes runtime comparison, status, or portal artifacts and does not change formed frontend code, foundation artifacts, or explicit blocker output, treat that pass as incomplete and continue Step 12 remediation.
- Override rule: if the user explicitly pushes past a failing gate, allow the skip only as an override with a warning that names the remaining risk and the biggest unresolved wins.
- Traceability rule: when a gate fails, return the exact failing dimension and the exact next step. Avoid generic retry language when the real blocker is visual parity, selector coverage, inventory coverage, or screenshot coverage.

## Evidence And Publishing Rules

- Evidence-source rule: use the newest gate-bearing artifact as the source of truth. If summary or status artifacts disagree with the current runtime comparison, reconcile them before returning a handoff decision.
- State-route fidelity rule: when distinct legacy screenshot states for one formed screen collapse to the same modern screenshot hash across different modern routes, treat that as a Step 12 failure in URL-owned state restoration rather than as acceptable screenshot reuse. Keep Step 12 open until the target shell restores the required query, tab, or auxiliary route state, or the comparison artifact proves the legacy states are not materially distinct.
- Portal wiring rule: verify which JSON artifact the portal page actually reads before editing status outputs. Fix the source artifact. Never auto-run portal refresh from a numbered step; portal refresh is a manual-only user action and numbered steps must complete from source artifacts. See `/.github/instructions/qa-portal-reporting.instructions.md`.
- Static portal serving rule: if the QA portal exists on disk but does not load in the browser, verify local HTTP serving before assuming generation failed.
- Refresh rule: after meaningful frontend changes, rebuild the selected browser client and rerun frontend tests. Return decisions from source evidence. Never auto-republish the portal; if portal pages lag the refreshed source artifacts, report the staleness in chat for the user to refresh manually.

## Product-Facing UI Rules

- Production-copy rule: modernization-stage language belongs in reports, not in the delivered app UI. Remove Step 12 or Step 13 process narration, decomposition, seam, wiring, or workflow language from user-facing screens.
- Report-vs-app rule: generated report UX may discuss formation, parity, deferrals, and next steps. The application itself must remain product-facing and source-faithful.

## Per-Route Behavior And Wiring Rules

- "Page renders" is not "page works." When Step 11 closes on build-green and selector preservation while migrated routes still expose `javascript:void(0)`, dead inline-script handlers, missing modal/banner triggers, or placeholder/seed/hard-coded data, the app reaches the Fusion UI swap steps looking polished but is behaviorally dead. Step 11 must port every legacy interactive element on every migrated route to a real Angular component binding, or explicitly classify each unresolved hand-off per route to Step 12 or later. Use `behaviorPreservationStatus` and `perRouteBehaviorList` to make this visible, and record every deferred stub handler in the deferral registry (`.modernization/ignition-artifacts/discovery/ui-deferral-registry.json`) with a truthful `ownerStep` so the drain gate can re-flag it if its owner step passes without wiring it.
- Auth-seam proof is not per-route wiring proof. When Step 12 closes on login/callback/logout/landing while migrated routes still render placeholder data because no service call was wired or no real backend route was hit, the platform looks integrated but the product is not. Step 12 must prove per route that the primary protected data calls actually fire from the modernized client, attach the approved auth mechanism, return the expected success status, and render real backend data - and, because Step 12 owns "no button is dead," it must drain the Step-11 behavioral deferrals it owns by running `scan-ui-parity-gaps.ps1 -CurrentStep 12` so a still-dead export/add/delete button fails the gate instead of shipping. Use `perRouteApiWiringStatus` and `perRouteApiWiringList`.
- Step 6 owns the per-route behavior plan at `.modernization/portal/data/json/per-route-behavior-plan.json` (one entry per in-scope route with `{route, primaryEndpoint, observedStatus, dataSource}`) to make this visible. Routes whose interactive controls or data calls are not enumerated at Step 6 are a Step 6 blocker, not a Step 11 or Step 12 discovery item - this is the only way to keep the kit repeatable on the next application without rediscovering the same dead-shell failure mode.
- Phase-discipline rule: when Phase 2 finds a route with dropped behavior or missing data wiring that Step 8 did not list, the loop is stop Phase 2 -> route back to Step 8 -> refresh the per-route behavior plan -> resume Phase 2. Do not let Phase 2 silently absorb the planning gap.


## Fusion UI Replacement Rules

These rules capture durable lessons from deliberate Step 15-16 primitive-family replacement work. They apply to every later app the kit touches.

- Binding-shape rule: classify every interactive control by its current binding shape at Step 14 (`twoWayNgModel`, `oneWayNgModel`, `uncontrolledValueEvent`, `reactiveFormControl`, `uncontrolledNoModel`). A wrapper that assumes ngModel cannot drop-in replace an uncontrolled `[value]+(input)="x.set(...)"` control without a binding-shape refactor. Step 15 and Step 16 must read this field before selecting a swap target.
- Options-as-model rule: when legacy `<option>` elements have no `value` attribute, the option text is the bound model value, not just a display label. Step 14 must flag these with `optionsAreLiteralModelValues: true`. Replacement option arrays must use `label === value` so the bound string semantics stay identical. Wrapper bindings must set `valuePrimitive=true` for these dropdowns.
- Migration-eligibility rule: parity-scaffold controls and reverse-engineering capture surfaces (for example `*-parity-*`, `*-selector-capture-*`, `*-hidden-*` naming families when present) must be marked `migrationEligible: false` in the inventory so they never surface as Step 15 or Step 16 candidates. This is a hard schema flag, not a convention.
- Composite-control rule: visually paired controls that form one semantic unit (numeric input with flanking adjuster buttons, search input with embedded action, etc.) must share a `compositeGroupId` in the inventory. Step 15 and Step 16 must swap composite groups as a unit or explicitly defer the unmigrated members with a recorded reason.
- Dynamic-id rule: controls whose `id` is template-interpolated per row or per index (`id="lrSum-{{i}}"`) must be flagged `dynamicId: true` and require a `testIdFn` or interpolation contract before swap. They cannot use the wrapper's flat `elementId`/`testId` inputs without a decision.
- Dialog-vs-shell rule: controls inside dialogs and modals belong in a dialog family (or dialog sub-family), not in the main-shell control family. Dialog controls have different focus, escape, and aria expectations and a different swap risk profile.
- Sub-pattern-per-pass rule: when a single primitive family contains multiple sub-patterns (different binding shapes, value types, or wrapper-capability requirements), Step 15 and Step 16 must execute exactly one sub-pattern per pass and report `subPatternProgress`. `familyRetirementStatus: Partial` with a named `followUpSlice` is the correct closeout for partially-advanced families.
- Wrapper-capability eligibility rule: Step 16 next-eligible selection must respect `requiresWrapperCapability` on a slice. A slice whose required wrapper kind (for example `kind: file`) does not yet exist is not eligible for advance; the next-action choice is either extend the wrapper first or skip the slice with a recorded reason.

## Wrapper Design Rules

These rules govern app-owned wrappers that front a Fusion primitive (for example `app-home-form-field` wrapping `fusion-dropdown` / `fusion-textbox` / `fusion-number`).

- Generic-options rule: a wrapper that fronts a generic Fusion primitive must expose the primitive's generic option type. Do not narrow `options` to a domain-specific shape (for example `ReferenceLookupOption[]`) by default. Use a permissive option type such as `Record<string, unknown>` plus explicit `displayPath` and `valuePath` inputs.
- Disabled-plus-readonly rule: any form-field-style wrapper must expose both `readOnly` and `disabled` inputs and derive a `controlDisabled = readOnly || disabled` computed for the underlying primitive. Non-reactive-form callers bind `[disabled]` directly; relying on a parent form-control to derive disabled is not sufficient.
- File-input coverage rule: if the Step 14 inventory contains `<input type="file">` controls, the form-field-style wrapper must either ship `kind: file` from day one or the wrapper extension must be planned as a Step 15 prerequisite. Do not silently defer file inputs every pass; record them as `requiresWrapperCapability: ["kind:file"]` and either close the gap or skip with a reason.
- Wrapper-input parity rule: before the first swap in a family, reconcile wrapper inputs against the Fusion primitive's full input surface using Fusion MCP. Add any missing wrapper inputs (`placeholder`, `min`, `max`, `step`, `decimals`, `rows`, `valuePrimitive`, `readOnly`, `disabled`, `elementId`, `testId`) in one pass at the start of the family so later sub-pattern passes do not need to extend the wrapper mid-stream.
- Test-hook preservation rule: wrappers must accept and forward `elementId` and `testId` inputs so legacy `<label for=...>` association and Playwright `data-testid` selectors keep resolving after the swap. A swap that drops either is a parity failure even when the build is green.
- Option-array typing rule: `as const` option arrays in caller components are encouraged for literal-string parity. The wrapper option type must be permissive enough to accept `readonly` arrays of literal-typed objects without a cast.


## Slice Parity And ROI Rules

These rules apply to every Phase 2 frontend modernization pass (Step 12, Step 13, Step 15, Step 16) so UI parity advances visibly to the user and biggest-ROI work happens first.

- **Slice the parity work, do not push for 100 percent in one pass.** Every pass advances one slice (one route plus one primitive family or sub-pattern). Target gain is 5 to 10 percentage points of route-state parity per pass.
- **Per-slice diff is mandatory.** Each pass emits before/after visual diffs for the touched `{routeId, stateId}` rows under `.modernization/portal/data/images/parity-diffs/{step}-pass-{passId}/` and records `{ parityBefore, parityAfter, parityGain }` on the slice entry in `ui-fusion-map.json`.
- **Recommend the next pass at every closeout.** Until the surface is exhausted, every pass ends with an explicit recommendation to rerun Step 15 or Step 16 with the expected next parity gain and the next-eligible slice named.
- **ROI-first selection.** Among dependency-safe and eligible slices, choose the one with the highest `(visibilityScore + interactionScore) - riskScore`. Score on a 1-5 scale and record the score on the pass.
- **Visible-impact-first rule.** The first three modernization passes on a new browser surface MUST produce a change the user can see and interact with on a primary route. Background refactors, passive containers, and tooling-only changes come after the user can see visible progress.
- **Surface order priority:** interactive primitives (buttons, dropdowns, dialog launchers, primary form inputs) before composite containers; primary routes before secondary; visible routes before deep-link-only routes; high-traffic flows before edge flows.
- **Generic across frameworks.** These rules apply to any source framework (MVC, Razor Pages, Web Forms, AngularJS, Angular, React, Vue, Blazor, server-rendered HTML). Capture and parity-diff are equally required for server-rendered and client-rendered surfaces.



## Live-Wire Click-Through Rules (durable)

These rules exist because cosmetic restoration repeatedly slipped past closeout while the route was functionally dead (visible HTML, broken data path). They MUST be honored by every Step 12, 13, 14, 15, 16, and 17 pass.

- **Data-bound first.** On every parity slice, prove the data path BEFORE the cosmetic path. A slice closes only when (a) the primary data calls on the route fire, (b) bind to the same query-string contract the legacy view sent, (c) return real backend rows (not preview-fallback rows), and (d) the rendered rows are visible in the DOM bounding box. A slice that ships visible markup over empty arrays is NOT complete.
- **Legacy-contract wins on query/path/verb.** When the modern API and legacy API disagree on a query-string parameter name, route segment, HTTP verb, or response shape, the modernized server MUST adopt the legacy contract unless the user has explicitly approved a contract break. Renaming the modern server to match the legacy view is the default fix; modifying the modern client to send new param names is only allowed when the legacy contract is being intentionally retired.
- **Click-through proof gate.** Every Step 13 visual-parity run AND every Step 15/16 slice closeout MUST exercise each interactive surface on the touched route at least once and prove that:
  - dropdowns open and reveal every documented child item,
  - tabs change content,
  - primary action buttons (Calculate, Save, Delete, Search) populate or mutate the surfaces they targeted in legacy,
  - row selection in a list hydrates the dependent panel.
  A "render-only" pass does NOT close the slice. If the parity script cannot drive the surface (no test seam), the slice closes only with an explicit recorded follow-up that names the missing seam and the next-pass plan to wire it.
- **Bootstrap-baseline rule for legacy-source markup.** Any modernized route that re-emits Bootstrap utility classes from a legacy view (`.row`, `.col-*`, `.table`, `.btn`, `.btn-*`, `.panel`, `.panel-*`, `.container-fluid`, `.searchBox`) MUST guarantee `styles.scss` re-baselines those classes. `@fusion/theme` does NOT provide them. Missing baseline is a Step 12 failure, not a Step 14 cosmetic followup.
- **Nested-interactive-inside-Fusion-primitive rule.** When an app-owned interactive control (dropdown toggle, action button, menu trigger) is rendered inside a Fusion primitive that owns its own click semantics (e.g. `fusion-tab-label`, `fusion-card-header`), `stopPropagation` is not sufficient. The host parent MUST cooperate by either (a) not resetting child state on the primitive's own activation event, or (b) hosting the interactive control as a sibling of the Fusion primitive rather than a descendant.
- **Step 6 per-route behavior plan is the gate.** Step 15 and Step 16 must classify every such nesting and pick (a) or (b) explicitly. Every interactive control AND every primary data call on every in-scope route MUST appear in `.modernization/portal/data/json/per-route-behavior-plan.json` before Phase 2 starts. If Phase 2 encounters a control or call that is not enumerated, it is a Step 6 omission, not a Step 11/12/15/16 discovery; the loop is stop -> Step 6 amend -> resume.
- **Param-name drift detector.** Step 12 and Step 14 MUST emit a `route-contract-diff.generated.json` artifact that lists, per modernized endpoint, the query parameter names the modern server binds vs. the names the modern client sends vs. the names the legacy view used. Any disagreement is a release blocker for that route.
- **No "looks done" without click evidence.** The agent MUST NOT report a route, slice, or step as complete based on screenshot match, build-green, or DOM presence alone. Closeout must include per-interactive-surface click evidence (or a recorded follow-up that names the missing seam).


## Runtime Parity And Move-First Rules (durable)

These rules exist because a modernized frontend shipped unrecognizable and missing features (empty shell nav, admin "Add Row" hidden behind an unwired flag, a grid re-created thinner than legacy) while every static gate passed. A reference restructure preserved features and styling by moving the real components and verifying at runtime. They apply to every Phase 2 frontend step that changes `src/`.

- **Move-first default.** The default migration verb is MOVE the real legacy component (template, styles, logic), get it building, then swap individual controls for Fusion primitives. Parity is the starting state you preserve, not a percentage you climb toward. A page rebuilt from memory that drops controls, row actions, popovers, or admin-gated buttons is a parity defect even when it compiles and looks close. Scaffold-from-empty is allowed only for genuinely new shell rooms, never as a substitute for porting an existing page.
- **Runtime checkpoint is mandatory for src-changing steps.** A step that changes runnable behavior is not complete on compile-green. Run `/.github/skills/runtime-parity-checkpoint/SKILL.md`, boot `src`, drive each in-scope route in the integrated browser, and watch BOTH the browser console and the backend log. Save `runtime-parity-checkpoint.json` with `navParity`, `controlVisibilityParity`, `dataBindingParity`, `consoleErrorCount`, and `backendErrorCount`. "Compiles" and "DOM element exists" are necessary but never sufficient.
- **Configured-but-not-rendering is a defect.** Route menu metadata that exists while the shell renders an empty `<nav>` is a navigation parity defect. The shell nav MUST render every configured route link and each link MUST navigate. A landmark or `data-testid` that exists with no rendered links passes the structural check but fails parity.
- **Present-but-hidden is missing.** A control that exists in the template but is hidden behind an unwired role or feature flag (for example an admin button gated by a placeholder `isAdmin` that is never set) counts as missing at runtime. Record it in `controlsHiddenBehindFlag` and either wire it in the same step or record an explicit, owned waiver. Deferring a visible legacy control behind a dead flag is not an acceptable closeout.
- **The control-parity scanner must stay honest.** `.github/scripts/parity/scan-ui-parity-gaps.ps1` must never silently drop an interactive legacy control. Every legacy button, link, routerLink, submit, or modal/dropdown trigger with no modern counterpart is a `MissingControl` Major gap (exit 2), and `unmappedInteractiveControlCount` plus `controlCoverageRatio` are honest coverage signals. If a scan ever reports zero gaps while the running app is clearly missing controls, fix the scanner's harvesters before trusting the gate again - a gate that manufactures false confidence is worse than no gate.
- **The scanner enforces field parity, not just control presence.** Beyond missing interactive controls, `scan-ui-parity-gaps.ps1` reconciles grid columns (`MissingColumn` Major: a grid that loads real data but in fewer or more generic columns than legacy - the "grid re-created thinner" defect) and detects inert controls (`InertControl` Major: a control present but bound to an empty/TODO handler or a literal `[disabled]="true"`). Legacy columns are harvested from both markup `<th>` and component `.ts` (ag-grid `headerName` / ColDef `title`), because a thinned grid often hides as a few generic columns while the legacy column set lived in the component class. A control that renders is not the same as a control that works, and a grid that loads data is not the same as a grid that shows the legacy fields.
- **A deferral must name an owner step and be drained there - allowlists are app evidence, not script code.** The inert-control suppression list must NEVER be hard-coded into `scan-ui-parity-gaps.ps1` (that is what let a shipped `exportToExcel` / `addRows` / `deleteSelected` stub set report `inertControlCount = 0` while the buttons were dead, and it embedded app-specific handler names in a reusable script). Instead, every temporarily-deferred stub lives in the per-app registry `.modernization/ignition-artifacts/discovery/ui-deferral-registry.json` as `{ handler, ownerStep, reason }`, where `ownerStep` is the numbered step that must actually WIRE the handler and whose completion gate verifies that class of behavior (a "no button is dead" control belongs to Step 12, not a vague "later"). Three rules keep this honest:
  - **Never invisible.** Every suppressed deferral is always emitted in the scan's `deferredInertControls[]` with its `deferredInertControlCount`, so a zero inert count can never be mistaken for zero deferred behavior. A step that reads `inertControlCount = 0` must also read `deferredInertControlCount` before trusting the gate.
  - **Drained at the owner step.** Run the scanner with `-CurrentStep <n>` at the owning step's closeout (and at Phase 2 close). Any deferral whose `ownerStep <= CurrentStep` is re-flagged as a Major `InertControl` (the drain gate, exit 2) - the deferral cannot survive past the step that promised to wire it.
  - **Owner step must own the behavior.** A behavioral deferral pointed at a step whose gate does not verify that behavior is a mis-owned deferral, not a valid waiver. Fix the `ownerStep`, or wire the control now. A behavioral deferral may never ride forward to the final review un-drained.
- **If a scan reports zero gaps while the running app is clearly missing controls, fix the scanner before trusting the gate.** A gate that manufactures false confidence is worse than no gate. When the scanner and the running app disagree, the running app wins: extend the scanner's harvesters (or drain the deferral registry) until the scan reflects reality. Suppress a genuine intentional removal with a written reason in the registry or a dimension allowlist, never by bypassing the gate.
- **Closeout steps may enforce a coverage floor.** Later/closeout frontend steps may run the scanner with `-CoverageFloor` to hard-fail when modern interactive control coverage is far below the legacy baseline. Keep it off (default 0) during early foundation passes where low coverage is legitimate.


## Legacy Visual Parity Rules (durable)

These rules exist because a modernized frontend reached the end of frontend migration looking nothing like the legacy app - a raw default framework theme, a navigation region with zero links, and no recognizable header or footer chrome - even though the legacy visual language was fully derivable from legacy source. Every static gate passed while the modern app was visually unrecognizable. They apply to every Phase 2 frontend chain the kit touches.

- **Answer key is the legacy app.** The visual-parity reference is always the legacy application in `LegacyCode/` plus the extracted legacy visual contract, never a finished modern reference. Real engagements do not have a modern twin to copy, and the legacy visual language (palette, typography, header/nav/footer chrome, nav route model, layout density) is mechanically derivable from legacy global CSS/SCSS and shell markup for any application.
- **Extract once, early.** Step 3 captures the legacy visual contract (static parse of palette/token variables, `@font-face`/typography, header/nav/footer markup, button/label rules; plus runtime computed styles and per-route reference screenshots when the legacy app runs). Step 5 consolidates it into `.modernization/fusion-restructure/styling-foundation.json` and `ui-visual-contract.json`. A thin styling foundation here is the root cause of an unrecognizable modern shell later, so treat a missing palette, typography, chrome, or nav-model capture as a Step 3/Step 5 gap, not a Step 10 discovery.
- **Apply by construction at Step 10.** Step 10 must generate app-owned design tokens from the extracted palette/typography, bind the Fusion theme to those tokens, and build the shell chrome (branded header, nav populated from the route inventory, footer, layout density) so the modern app inherits the legacy visual language from the first page paste. An empty nav and a raw default framework theme are explicit Step 10 failures.
- **Compare before swapping.** A dedicated visual-parity gate runs at the Step 13 closeout and must be `pass` before Step 14 begins Fusion primitive swapping. Reuse `/.github/skills/visual-parity-gate/SKILL.md`; it boots legacy and modern dual-port, captures matching routes, diffs computed styles plus screenshots against the contract, and emits `.modernization/fusion-restructure/visual-parity-report.json` with per-route pass/partial/fail across palette, typography, header/nav/footer presence, and layout. Do not begin Step 14+ while the modern app does not resemble the legacy app unless the residual gap is explicitly accepted with recorded reasons.
- **Live side-by-side is an aid, the diff is the gate.** The dual-port legacy-and-modern side-by-side view helps a developer spot drift quickly, but the enforced gate is the automated computed-style-plus-screenshot diff in the report, not an eyeball check.

## Legacy Styling Binding Rules (durable)

These rules exist because a modernized frontend extracted the legacy palette, typography, and sizing correctly into `styling-foundation.json` (brand-blue header, Lato, light theme) yet still rendered a dark, unbranded shell with the wrong header color and the wrong field sizing. Extraction succeeded; binding failed. They apply to every Phase 2 frontend foundation pass and were confirmed against the `@fusion/theme` framework docs via Fusion MCP.

- **Extraction is not application.** Correctly extracting the legacy palette/typography/sizing into the styling foundation proves nothing about the running app. The values must be BOUND through the mechanism the components actually consume. A `styling-foundation.json` with the right colors plus a shell that renders the framework default is a binding failure, not an extraction win.
- **Never brand via orphan CSS custom properties.** A generated `--color-brand-header-bg` (or any `--color-*` token) that no theme generator, selector, or component reads is orphaned and changes nothing on screen. Tokens are only applied when a consumed variable, a theme-generator override, or a component style reads them.
- **Bind through the theme system's real API.** Inject the legacy palette/typography/sizing through the API the components consume. For `@fusion/theme`, that is the light/dark theme-generator **override map** plus the `root/main` **header-branding** composition (the `@fusion/theme` README documents both; confirm the exact override-map keys via Fusion MCP before binding - do not guess). When a legacy styling system is preserved for parity (Bootstrap, Material, and similar), inject the legacy brand into that system's config map (for Bootstrap, the `$bootstrap-config` consumed by `bootstrap/scss/bootstrap`).
- **Preserve the legacy styling system first; swap the theme system deliberately later.** Parity-first means keeping the legacy styling system configured with the legacy brand during Steps 10-13 so the app looks like legacy by construction. Ripping out the legacy styling system and substituting a different theme system before parity is established produces an unbranded default theme. Bind the Fusion theme to the legacy tokens when swapping components in Steps 14-16, not before parity is proven.
- **Force the legacy color scheme.** When the legacy app is light, the shell must apply the light theme deterministically. A shell that renders dark because of an OS `prefers-color-scheme: dark` media query or an auto-added `dark-theme` class while the legacy app is light is a defect, not user preference. Force the legacy color scheme; do not inherit the OS preference.
- **Header color and field sizing are first-class contract.** The legacy header background and the legacy form-control sizing/density (input height, border, label size) are part of the visual contract. Bind them through consumed variables and verify them in the visual-parity gate's computed-style diff, not by eyeball.

## Render-Proof Enforcement (durable)

These rules exist because a frontend foundation and migration chain reported `visual-parity-report.json` and `runtime-parity-checkpoint.json` as `pass` while the running app rendered in the wrong color scheme (dark over a light legacy app), with an unbranded header, full-bleed form controls, and routes throwing `4xx`/`5xx` in an authenticated session. Every static gate was green. The rules and gates to catch this already existed; the failure was substituting proxies for an actual render. They apply to every Phase 2 step that changes `src/` and to the visual-parity and runtime-parity gates.

- **A gate verdict must come from an observed render, never a proxy.** A successful client build, a parity-scanner `majorGaps=0`, and an SPA route returning HTTP 200 are necessary but never sufficient evidence of visual or runtime parity. They prove the bundle compiles and the route is served, not that the page renders the legacy scheme, chrome, sizing, and real data. A `visual-parity-report.json` or `runtime-parity-checkpoint.json` written from build/scanner/HTTP signals instead of an actual rendered browser observation is invalid evidence, not a pass.
- **Data-binding parity requires an authenticated session and observed rows.** An unauthenticated probe (curl or browser) that returns `401` proves only that the route is registered and protected. It is NOT `dataBindingParity: pass`, and "expected to work once authenticated" is unverified, not passed. The runtime checkpoint must run in an authenticated session, fire each route's primary data calls, and observe real rows in the DOM while watching the backend log for `4xx`/`5xx`. A route whose authenticated load returns a validation `400`, a server `500`, or an empty/placeholder grid is a `dataBindingParity: fail`, regardless of how the unauthenticated probe behaved.
- **Do not carry forward a prior session's observations as current evidence.** Each gate run must observe the current `src` state. Re-stamping an earlier run's row counts or screenshots as the current verdict hides regressions introduced since. If the current environment cannot perform the authenticated render (no auth session, app will not boot), report the gate `blocked`/`unverified` and keep the step open - never write `pass` from assumption.
- **Name the color-scheme control point.** The browser starter `index.html` typically ships a script that adds a `dark-theme` class from the OS `prefers-color-scheme: dark` media query. For a fixed-scheme legacy app, that script makes the modern app follow the developer's OS instead of the legacy scheme, so the same build renders light on one workstation and dark on another. Pin the legacy scheme deterministically (neutralize or replace that script and/or force the scheme through the theme config) and verify the rendered `background-color` of the header chrome in the visual-parity computed-style diff.

## Reference-Confirmed Styling Mechanics (durable)

These concrete mechanics were confirmed by comparing a thin modern shell (full-bleed controls, unbranded chrome) against a known-good reference restructure of the same legacy app. They are portable across browser-led SPA targets; capture the pattern, not the specific values.

- **Prefer the framework default theme chrome over orphan brand overrides.** The framework default theme often already carries the legacy brand chrome (header/footer background, primary-button color) because the legacy and framework brand palettes match closely. Adding a brand-token override map that no rendered surface needs adds risk without changing the result. Override brand tokens only when the legacy palette genuinely differs from the framework default, and prove the difference in the rendered computed-style diff.
- **Control sizing needs configured style include paths and shared partials.** Full-bleed form controls that span the page width are usually a missing-layout defect, not a per-control style gap: the client build has no shared style include paths configured (the style preprocessor `includePaths` is empty) and no shared layout partials, so per-component styles cannot constrain field width. Step 10 must configure the client build's style include paths and provide the shared layout partials (variables, mixins, collection/grid layout, side-nav) that page components consume, so controls inherit constrained widths by construction.
- **Wrap filter and form controls in width-constrained field containers.** Emit each filter/form control inside a constrained field container (a form-group/field wrapper with inline-label and spacing rules) rather than as a bare full-width primitive. A primitive emitted with no width constraint stretches to its container; the legacy layout constrained it.
- **Data grids declare explicit per-column widths.** A grid that lets every column auto-size diverges from the legacy column widths and density. Declare explicit per-column widths (plus pageable/sortable/height settings) so the grid renders at legacy density.
- **Set button color through the primitive's color API.** Give each button its legacy color via the primitive's color inputs (for example a theme-color plus fill-mode input) rather than leaving it at the default or relying only on a global override. Link-style buttons keep the legacy link treatment.
- **Preserve legacy navigation affordances.** When a legacy route used a left/side navigation to switch sub-views, preserve that affordance (a side-nav container driven by the route's view model) instead of collapsing it into a single dropdown. Swapping the navigation shape is a layout-parity regression even when every sub-view is reachable.
- **A deterministic static gate makes this first-pass on any app.** The render checks above depend on an agent actually rendering; a static gate does not, so it is the durable backstop. `.github/scripts/parity/scan-styling-foundation.ps1` statically fails a Step 10 closeout when the client `index.html` follows the OS `prefers-color-scheme` instead of the pinned legacy theme, when the include path holds no shared partials, or when a data grid's columns are all auto-sized. It needs no running app and is app-agnostic (derives the legacy scheme from `styling-foundation.json`, discovers the client root and grids generically), so it catches the dark-shell / full-bleed-control / auto-sized-grid failure modes on the first pass for every application. Keep it wired into the Step 10 gate and extend its harvesters rather than bypassing it.
